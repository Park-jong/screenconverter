# 4-12 피드백: ASCII 아트 (feedback-synthesizer 보고, 메인 에이전트가 대신 저장)

근거: 4-10 개발 보고, 4-11 검증 보고, ROADMAP 4′단계, `EffectPackageImportsTest` 소스 직접 확인(그 외 소스는 4-11 코드 리뷰 결과를 신뢰, 빌드·실행 없음).

## 판정
- **ASCII 단계: 완료(사용자 육안 확인 대기)**. 동작 실패 0건, 높음·중간 없음. 증거: 테스트 65개, 손계산 하드코딩(k 매핑, 부분 칸 분모 — 분모를 16으로 잘못 쓰면 k=2가 되어 잡힘), 독립 레퍼런스 2896건 + 밝기식 2^24 전 조합 + k 매핑 16,384 조합 전수, 통합 63케이스 failing=0 + 1~8 회귀, 음성 대조(두 색·글리프 일치만으로는 못 잡고 정확 비교·단조성으로 잡힘 → 검증기가 둔하지 않음), 동적 약 5,900프레임, 성능 3.7/4.9ms·CPU 약 5~7%, 회귀(affinity 0x11, topmost, 드래그, 최소 크기, 닫기) 통과. 공백: DWM 합성 화면 직접 육안(구조적 불가), 실제 브라우저·IDE 텍스트 화면·동영상(합성 그림으로 대체), DPI 125/150%·다중 모니터·장시간 메모리(5단계 기존 공백), ESC(클릭 없이) 이월(변경 전 상태와의 직접 대조는 못 함). 4-11의 `D9` propBad=1은 하네스 버그(`D9c`에서 PASS).
- **4′ 전체(흑백·도트화·ASCII)**: 자동 검증 기준 완료, **사용자 육안 통과 시 4′ 최종 종료**. 남은 기준은 "사용자 육안"(모자이크 4-3부터 누적된 필수 1회)뿐. ASCII의 "읽기 어려움"은 결함이 아니라 설계 한계 — 불만이면 6단계 옵션 우선순위 조정으로 처리.

## 사용자 육안 안내(요약)
이미지·사진이 많은 창 위에서 오버레이를 크게 키우고 키 1~9를 차례로 눌러 제목이 바뀌는지 확인. 2번은 큰 네모 블록, 3번 회색조, 4번 흑/백 두 색뿐, 5번 EGA 16색, 6번 초록 계열 4색, 7번 원색 블록 + 얇은 어두운 격자선, 8번 16색 + 격자, 9번은 흰 바탕 검은 문자만 — 밝은 곳은 공백·`-` `'` `:`, 어두운 곳은 `8 % $ # & W @`(방향이 반대면 문제), 큰 도형 윤곽이 문자 덩어리로 알아볼 만한지, 8x16 격자 정렬. **작은 글자·텍스트 화면이 거의 공백이 되는 것은 정상**. 창을 드래그·리사이즈해도 끊기지 않고 따라오는지, 오버레이 자신이 찍혀 무한 반복(거울)되지 않는지(DWM 합성 화면을 사람이 보는 핵심). 이상이 있으면 스크린샷과 키 번호.

## 낮음/정보 처리
- **(a) EffectPackageImportsTest 허점 3종**(금지 목록 밖 Component 하위, 완전수식 사용, 한 줄 다중 import): **allowlist 방식으로 뒤집기 권장** — ① 주석·문자열 리터럴 제거(package-info 주석이 금지 이름을 언급) ② `;`로 문장 분리 ③ 소스 전체에서 정규식 `\b(java|javax|com|org|jdk|sun)\.[a-z]+(\.[A-Za-z_*][\w*]*)+`로 모두 찾기(import 문장뿐 아니라 본문 완전수식도) ④ 허용 목록과 대조 — 정확 일치 `java.awt.Color`, `Font`, `FontMetrics`, `Graphics2D`, `RenderingHints`; prefix `java.awt.image.`, `java.awt.font.`, `java.util.`, `java.lang.`, `java.io.`, `java.nio.`, `java.util.function.`, `com.converter.effect.` ⑤ 목록 밖은 모두 실패(`import static`은 마지막 멤버를 떼어 같은 방식). 검출기 단위 테스트에 `java.awt.Button`, 완전수식 본문, 한 줄 `import a; import b;`, 주석 속 이름 무시, 허용 클래스 통과 추가 + `java.awt.Button` 주입 시 FAIL 음성 대조. 30~50줄 규모. **지금 해도 되고 5단계 시작 전 테스트 보강에 묶기를 권장**(5단계에서 공통 유틸이 effect 패키지에 들어오므로 그 전에 안전망을 닫기, 새로 허용할 import는 목록에 명시적으로 추가해 변경 이력으로).
- **(b) GlyphSet "잉크 오름차순" 계약**: 생성자 검증 대신 구현체 책임으로 두고 `GlyphOrdering` 단일 경로에 대한 구현체 테스트("strictly 오름차순, 첫 글리프 공백")로 확인. 6단계 문자 세트 선택 때 함께 결정(저비용 대안은 비감소 확인 후 IAE, 동점 허용 여부 정의 필요).
- **(c) 글꼴 후보 공개 API**: 지금 불필요. 6단계에서 글꼴 선택 UI가 필요하면 `FontGlyphSet(List<String> candidates, int cellWidth, int cellHeight)` 추가(기존 2인자는 기본 후보로 위임), 그때 리플렉션 테스트를 일반 테스트로 전환. 글꼴 차이는 Consolas가 가장 선명 정도라 우선순위 낮음.
- **(d) `FontGlyphSet(1,1)` 퇴화**: 현재 어떤 경로에서도 발생하지 않음. Javadoc 한 줄(또는 최소 크기 검증, 예: 4x8), 6단계 칸 크기 UI가 최소값을 제한할 때 처리.
- **(e) EffectRegistry Javadoc 오타**: 다음에 EffectRegistry를 열 때(10번째 효과 또는 6단계) 한 줄 수정.
- **(f) 8x16 이진 마스크가 거친 문제**: 의도된 설계(정수 정확 비교 유지). 6단계 옵션 우선순위·비용: ① **칸 크기 선택 8x16/6x12/4x8**(체감 가장 큼, 비용 낮음 — 검증이 이미 4x4·3x5·8x8·16x32까지 통과, 4x8은 칸 수 약 4배라 추정 약 15ms로 5단계 계측 필요) ② 감마/정규화(중간 밝기 구간이 넓은 문제 개선, k 매핑에 LUT 추가, 검증 수식 재작성) ③ 반전(흰 글자/검은 배경: 문자가 잉크 오름차순이므로 배경을 검게 하면 매핑 반전 필요)·문자 세트 선택(GlyphSet 구현체만 추가) ④ 컬러 ASCII(글리프 색별 합성이라 arraycopy 최적화가 깨지고 마스크 알파 합성 필요) ⑤ 알파 마스크 합성(품질 최고, 검증 체계 전면 재작성·허용 오차 기준 신규 — 사용자가 요구할 때만).
- **(g) 작은 글자가 공백으로 평균되어 사라지는 한계**: 칸 평균 밝기 기반이라 설계상 당연(ASCII 아트는 큰 구조 표현이 목적). 개선은 별도 옵션 모드로 — 칸 내 최소 밝기, 평균과 최소의 가중합, 칸 내 표준편차 기반 대비 강조(정확도 기준과 하네스를 별도로 정의). 사용자가 텍스트 화면 변환을 주 시나리오로 삼을 때만 우선순위를 올리고, 아니면 기록만.

## 이월 항목 (4′ 종료 기준)
- **5단계**: DPI 125/150% 좌표 보정(위험 높음 — 실제 PC에서 어긋날 수 있고 captureRect 전체에 파급), 다중 모니터·음수 좌표(중간~높음), 프레임 스킵(낮음), 배열 재사용(중간 — 스레드·입력 불변 보장에 영향, 더블 버퍼 필요), 제외 실패 경고(낮음), Error/Throwable 포획(낮음), 장시간 메모리·핸들(중간, 측정이 오래 걸림), DataBufferInt 직접 접근 공통화(중간, 5개 효과에 걸침), 블록 평균 중복 정리(Mosaic/PixelDot/AsciiArt, 중간), 밝기식 복제 정리(Grayscale/AsciiArt, 낮음).
- **6단계**: 둥근 모서리 5px, 메뉴 폭 변경 시 최소 크기 재계산, ESC 포커스 이월(3-3 (c) 이래), 효과/옵션 UI(도트화 팔레트·격자 독립 토글, 흑백 2색 임계값, 블록 크기 `+`/`-`, 일시정지), ASCII 옵션((f) 순위), 글꼴 선택 API 필요 여부, GlyphSet 계약 검증, FontGlyphSet 최소 크기, 숫자 키 9개 한도가 UI로 대체되면서 레지스트리 번호 의미 재정리.
- **7단계**: 사용자 육안 체크리스트(DWM 합성 화면, 효과 1~9 포함 필수), 원격 데스크톱·폴백(제외 API 미지원 환경), fat jar·`.bat`·README, 추가 효과 후보(자동 팔레트 median cut/k-means, 디더링 — 4′ 범위에서 제외).

## 5단계 작업 순서 제안(조정판)
0. **계측(최우선)**: 현재 모든 효과가 최대 해상도에서 33ms 주기 안(원본 13.6ms, ASCII 3.7ms 등) → 효과 계산은 병목이 아님. 병목이 Robot 캡처(가장 큼)·페인트·스레드 지연 중 어디인지 먼저 확인하고 그 결과로 프레임 스킵·배열 재사용의 필요성을 가름(불필요할 수도). 1. **테스트 보강**: EffectPackageImportsTest allowlist(위 (a)), 정확 비교 하네스의 회귀 안전망화. 2. **DataBufferInt 직접 접근 공통화**: Identity → Mosaic → Grayscale → PixelDot → AsciiArt 순서로 하나씩(효과 1개마다 하네스 전체 실행 후 다음으로, 한 번에 5개를 바꾸지 않음). 3. **블록 평균 중복 정리**: 공통화 직후 `cellAverages`와 부분 칸 평균식 `(sum+count/2)/count`를 한 곳으로(부분 칸 분모는 오류가 나기 쉬워 손계산 하드코딩 테스트 필수). 4. 프레임 스킵(계측에서 필요성이 확인된 경우만). 5. 배열 재사용(계측에서 GC 압박이 보일 때만, 출력 이미지 재사용 시 이전 프레임이 페인트 중일 수 있어 더블 버퍼링 필요, 공통화 이후). 6. 제외 실패 경고·Throwable 포획(독립적·저위험, 워커 구조를 바꾸는 프레임 스킵과 함께 하면 충돌 감소). 7. **DPI/다중 모니터 좌표**(사용자 환경 답변에 따라 앞당기거나 미룸, 효과 리팩터링과 분리된 영역이라 병행 가능). 8. 장시간 메모리(구조 변경이 모두 끝난 뒤 마지막에 한 번).
- **공통 유틸 추출 시 회귀 안전망**: 5개 효과가 직접 접근 패턴을 복제하고 있어 한 번 틀리면 5곳에 퍼짐 → 4-5(흑백)·4-8(도트)·4-11(ASCII) 독립 레퍼런스 하네스를 scratchpad에 흩어 두지 말고 재실행 가능한 형태로 보존(이미지 타입 9종 × 크기 12종 × 서브이미지(오프셋 raster, scanline stride 37) 조합이 `directPixels` 폴백 경로까지 검증 — 판정 로직이 한 곳으로 모일 때 폴백 경로가 가장 깨지기 쉬우므로 이 조합 전수 비교 필수), 효과 1~9 × 6개 크기 + 최대화 통합 비교(D9 형태)와 음성 대조를 최종 단계에 한 번, 변경 전·후 출력 해시를 같은 입력에서 비교(가장 쌈), 성능 회귀는 효과별 중앙값을 같은 방식(워밍업 100회 후 300프레임)으로 전후 비교.
