## 구현
- **스케줄링**(`capture/FramePacer.java` 신규 순수 로직 + `ui/OverlayWindow.java`): `scheduleWithFixedDelay`를 없애고 데몬 스레드 "capture-worker" 루프(`captureOnce` → `pacer.afterFrame(now)` → `LockSupport.parkNanos(wait)`). 다음 시각 = `nextFrameTime + period`, 일찍 끝나면 남은 시간만 대기, 늦으면 대기 0으로 바로 다음 프레임을 시작하고 `nextFrameTime`을 now로 재설정(밀린 프레임을 몰아서 실행하지 않음), 통째로 지나간 슬롯 수는 `skipped()`로 계수. `converter.fps` 기본 30, 1~240 클램프, 잘못된 값은 30, "0"·"max"(대소문자 무관)는 대기 없는 연속 캡처. 종료는 `closeApp`에서 `captureThread.interrupt()` → `dispose()` → `System.exit(0)`, 루프는 `isInterrupted()`로 탈출.
- **EDT 적체 방지**: 워커는 `AtomicReference<Frame>` 슬롯에 최신 프레임만 넣고(이전 프레임이 아직 있으면 교체하며 `recordReplaced`로 계수), `AtomicBoolean displayPending`이 false→true로 바뀔 때만 `invokeLater(showLatest)`. `showLatest`는 플래그를 먼저 끄고 슬롯을 비워 표시 → 그 사이 들어온 프레임은 이번 표시에 포함되거나 새 invokeLater를 만들어 마지막 프레임이 항상 표시됨. `FrameMetrics`에 `setSkipped`·`recordReplaced` 추가, 출력 줄 끝에 `skipped=N replaced=N`(기존 필드 순서 불변).
- **Error 포획**(`capture/ErrorThrottle.java` 신규 + `OverlayWindow.captureLoop`): `Throwable`을 잡아 로그하고 계속, `InterruptedException`이면 종료. 같은 키(예외 클래스 + 메시지)는 5초에 1회만 `printStackTrace`, 억제된 횟수는 다음 출력 때 한 줄로 알림, 새 키는 즉시 출력. 정상 경로 출력 0.
- **제외 실패 경고**(`ui/ExclusionNotice.java` 신규 순수 함수 + `OverlayWindow`): 훅 실행 후 `captureExcluded`가 false이면 제목 끝에 " (제외 실패)" + `System.err` 한 줄 1회. `MenuPanel` 미수정. `selectEffect`는 `baseTitle` 갱신 후 `refreshTitle()`이라 접미사가 지워지지 않음. 훅 실행 전(`Main`의 `selectEffect(2)` 시점)에는 접미사 없음(`exclusionChecked` 플래그). 이 PC에서는 제외 성공(측정 로그 8건 모두 stderr 비어 있음).
- **BaselineDriver**: `-Ddriver.jvmargs="-Dconverter.fps=60"`로 추가 JVM 인자 전달 가능, 결과 표 "시도/표시"에 skipped·replaced 함께 출력.
- 미수정: `effect/*`, `win32/*`, 훅 순서, 창 장식, `MinimumWindowSize`, `MenuPanel`, `CapturePanel`.
- 신규 테스트: `FramePacerTest`(일찍 끝남, 늦음 후 재기준, 연속 지연 시 몰아치기 없음, skipped 수, 무제한, 프로퍼티 클램프·파싱), `ErrorThrottleTest`, `ExclusionNoticeTest`(가짜 DisplayAffinity), `FrameMetricsTest` 포맷 기대값을 skipped/replaced 필드 형태로 수정.

## 사실 정리
- **30fps 목표 달성**: 두 크기·두 효과 모두 30.1fps(기준선 21~17fps), grab·effect·표시지연은 거의 그대로 → 고정 지연 + grab 합산 구조가 fps를 깎던 원인이라는 5-1 해석과 일치.
- **30fps에서 간격 p95가 약 49ms**(평균 33.3ms): 평균은 맞는데 일부 간격이 33ms보다 크게 나옴. 원인은 확인하지 않음 — `parkNanos`의 윈도우 타이머 정밀도 또는 EDT 표시 지터로 추정만.
- **CPU(1코어 %)**: 640x360 기준선 3 → 30fps 6~7 → 60fps 10~15 → max 22~27, 1280x720 기준선 14~17 → 30fps 21~23 → 60fps 31~37 → max 56~57. 1280x720에서 60fps는 50fps대에 머묾(pacer가 놓친 슬롯 3~6).
- **max(상한 없음)**: 640x360 약 144fps(모니터 주사율 근처로 추정, 확인 안 함), 1280x720 약 67~72fps — grab 시간(640x360 6.4~6.6ms, 1280x720 약 11.5~11.8ms)이 상한 역할로 보임. max에서 1280x720의 GC 횟수가 11회·6회로 오히려 줄었는데 이유는 확인 안 함.
- **EDT 적체**: 모든 실행에서 교체 0, 시도≈표시 → 슬롯 교체 경로는 실제로 실행되지 않았고 확인된 것은 정상 경로의 동작.
- **기본값 판단용**: 30fps는 CPU가 기준선에 가깝고(6~23%) 목표 만족, 60fps는 CPU 약 1.5~1.7배(10~37%)에 1280x720에서 50fps대. 기본값은 일단 30.
