# 4-9 피드백: 픽셀 도트화 (feedback-synthesizer 보고, 메인 에이전트가 대신 저장)

## 판정: 도트화 단계 완료 (심각도 있는 결함 없음)
소스 직접 확인: `PixelDotEffect.java`, `EffectRegistry.java` (Palette.java는 읽지 않고 4-8 보고에 의존).
- ROADMAP 대조: 팔레트 제한·격자선 각각 켜고 끄기(`(blockSize, Palette, gridLines)`), 고정 팔레트(`Palette.fixed`, `GAMEBOY_4`, `EGA_16`, `NONE`), 등록 5~8(9 비어 있음, 키 9는 실측에서 무시) 모두 충족.
- 증거: 독립 레퍼런스 1561건, 통합 56건 25.4M픽셀 bad=0, `Palette.nearest` 두 팔레트 각 16,777,216색 전수, 키 입력(1~8 + 숫자패드, 9/0/A 무시, jar 프로세스), 동적 591프레임·110회 전환, 음성 대조 4종(정상 주입 대조군 통과) — 강함. 육안은 보통(DWM 합성 화면 미확인).
- 소스 일치: `directPixels`는 타입 INT_RGB/INT_ARGB, 뱅크 1개, `getOffset()==0`, `SinglePixelPackedSampleModel`이고 `scanlineStride==w`, `sampleModelTranslate` 0/0, 배열 길이 ≥ w*h일 때만 `DataBufferInt`를 복사 없이 읽고 하나라도 어긋나면 null → `getRGB` 폴백(4-8 판정 조건과 정확히 같음). 알파는 마스크로 걸러짐. INT_ARGB_PRE·INT_BGR은 폴백. 격자는 블록 첫 행 전체 + 나머지 행의 왼쪽 열 1px, 부분 블록에서도 `x1`을 넘지 않음. 평균 반올림 `(sum+half)/count`, `count=rows*폭` (Mosaic과 동일).
- 주의: `getData()` 호출은 입력 이미지를 가속 캐시 대상에서 제외(untrackable)시킴. 지금은 캡처 이미지가 프레임마다 새로 만들어져 영향 없음 → 5단계에서 이미지를 재사용하게 바꾸면 재검토.
- 남는 공백(차단 아님): DPI 125/150%, 다중 모니터·음수 좌표, 장시간 메모리·핸들, 숫자패드 NumLock 실키, DWM 합성 화면 육안, 사용자 육안 확인(도트화·ASCII 후 한꺼번에), 클릭 없는 ESC(6단계).

## 낮음/정보 처리
- **(a) EGA 회색이 평면으로 뭉침(디더링 없음)**: 이번엔 수정하지 않고 6단계 옵션 후보(기본 끔, Bayer 4x4 정도의 순서 디더링을 팔레트 옵션으로). 디더링은 "블록 내부 단색" 검증 속성을 깨므로 도입하면 레퍼런스·속성 검사를 새로 만들어야 함.
- **(b) IdentityEffect 15.7ms vs 도트 3~4ms**: 5단계 "DataBufferInt 직접 접근 공통화"로 배정. 순서(위험 낮은 것부터): ① IdentityEffect(복사만, 출력 타입 계약 새 INT_RGB 유지) ② MosaicEffect(도트와 같은 블록 평균이라 (e)와 함께) ③ GrayscaleEffect(4-5의 1677만 조합 전수 검증을 회귀 보호로). 위험 관리: `directPixels` 판정은 복제하지 말고 패키지 내부 유틸 하나로 추출(4-8이 getSubimage 11종·stride·오프셋 래스터로 이미 검증), 효과마다 최적화 전후 출력 비트 단위 비교(기존 독립 레퍼런스 재활용).
- **(c) 숫자 키 9개 한도**: 1~8 등록, 9는 ASCII. 이후 효과는 6단계 UI(선택 메뉴/순환 키). 키 체계는 건드리지 않음.
- **(d) 격자 색·굵기 고정(0x202020, 1px)**: 옵션화하지 않음(`GRID_COLOR` public 상수, 테스트·검증이 값에 의존, 육안상 과하게 덮지 않음). 6단계 변형 조합 UI 때 판단(옵션화하면 생성자 인자 추가와 `MIN_GRID_BLOCK_SIZE` 굵기 비례 재계산 필요).
- **(e) 블록 평균 중복**: 지금 리팩터링하지 않고 ASCII 구현 후 5단계에서 정리(ASCII 칸 평균이 세 번째 소비자 → 세 사례를 본 뒤 추상화, 검증 끝난 MosaicEffect를 지금 건드리면 재검증 필요, "NONE+격자 off == Mosaic" 교차 검증 존재). ASCII 4-10에서는 칸 평균 계산을 처음부터 별도 메서드로 분리해 5단계 추출을 쉽게. 정리 때 규칙 `(sum+n/2)/n`, 원점 (0,0), 부분 블록은 실제 픽셀 수 분모 유지, 기존 1561건 레퍼런스·56건 통합을 회귀로.

## ASCII 아트(4-10~4-12) 주의점
1. **effect 패키지 규칙 재정의**: java2d(`Graphics2D`, `Font`, `FontMetrics`, `GlyphVector`)는 컴포넌트가 아니라 이미지 렌더링이므로 허용. 금지: `javax.swing.*`, `java.awt.Component` 계열(`Window`, `Frame`, `Canvas`, `Container`, `Toolkit`, `Robot` 등), JNA, win32/UI 패키지 참조. 허용: `java.awt.image.*`, `java.awt.Font`, `FontMetrics`, `Graphics2D`, `RenderingHints`, `Color`, `java.awt.font.*`. 가능하면 import 검사 테스트로 만들고, 4-8의 기존 검증 기준("`java.awt.image.*`와 `java.util.*`만")과 규칙 문장을 같이 갱신. 테스트는 글리프 소스를 주입해 환경(헤드리스 등)에 의존하지 않게.
2. **글리프 캐시**: 생성 시점에 문자마다 칸 크기(8×16) 마스크를 사전 렌더링하고, 매 프레임 칸별 선택 문자의 마스크로 `int[]` 출력에 흰색/검정을 정수 연산으로 직접 씀(매 프레임 `drawString` 금지). 잉크 없는 문자(공백)는 칸 전체 `Arrays.fill`. 행 단위 처리, 폭 8이면 행당 한 바이트 비트마스크도 가능.
3. **밝기 → 문자 매핑**: 문자 세트를 실제 렌더링한 글리프의 잉크 밀도(어두운 픽셀 수)로 정렬해 매핑 자동 생성(글꼴이 바뀌어도 "어두운 칸 = 빽빽한 문자" 보장), 하드코딩 `" .:-=+*#%@"`는 후보 목록으로만. 밝기는 GrayscaleEffect의 정수식 재사용(4-5 전수 검증). 평균 밝기 `L`(0..255)을 N개 균등 반개구간 `[k*256/N, (k+1)*256/N)`으로 나눠 정수로 매핑(문서화·테스트). 잉크 밀도가 같은 문자는 중복 제거 또는 문자 코드 순서로 앞선 것. 밝기 0 = 가장 빽빽한 문자, 255 = 공백(잉크 0). 감마/대비 보정은 1차에서 제외(육안 후 필요하면 [min,max] 정규화를 6단계 옵션으로).
4. **고정폭 글꼴/비결정성**: 후보 Consolas → Courier New → `Font.MONOSPACED` 순, 실제 글꼴로 해석됐는지 확인해 폴백. **글리프 소스를 인터페이스로 주입**(예: `GlyphSet`: 문자 목록·칸 크기·문자별 마스크). 제품은 java2d 렌더링 `FontGlyphSet`, 테스트는 손으로 만든 결정적 비트맵 3~5개의 `FakeGlyphSet`.
5. **칸 크기/가장자리**: 칸 8×16 기본, 글꼴 크기는 칸 높이에 맞춰 정하고 advance 폭이 달라도 마스크는 칸 크기로 잘라 생성. 칸의 배수가 아닌 가장자리는 규칙을 하나로 문서화 — 권장: 부분 칸도 실제 픽셀 수를 분모로 평균을 구해 문자를 고르고 마스크는 해당 영역만큼 잘라 그림(도트화의 부분 블록 규칙과 일관), 대안은 흰색으로 비움. 어느 쪽이든 이미지 경계를 넘어 쓰지 않음(테스트 항목).
6. **방향/안티앨리어싱**: 어두운 칸은 빽빽한 문자(`@#8&`), 밝은 칸은 공백·`.`, 배경 흰색·글자 검정. 마스크는 이진 임계화(임계값 상수 명시)로 결정적으로(정수 연산, 검증 쉬움, 안티앨리어싱 설정에 둔감, 단점은 8×16에서 모양이 거칠어질 수 있음). 회색 합성은 육안 확인 후 알파 마스크(0..255, 정수식 합성, `RenderingHints` 명시)로 확장 가능.
7. **레지스트리 9 등록**: `EffectRegistry.defaults()` 맨 끝에 ASCII 등록(기존 1~8 순서 유지). `EffectRegistryTest` 갱신(항목 수 8→9, 미등록 번호는 10 이상, `register` 테스트의 새 번호 9→10). 검증의 키 입력 기대도 "9 무시"에서 "9 = ASCII"로.
8. **성능 예산**: 1738×1007에서 8×16 칸이면 약 218×63 ≈ 13,700칸(지시문의 27,000은 칸 높이 8 기준이거나 더 작은 칸일 때의 수치로 보이므로 구현 시 실제 칸 수로 다시 계산). 평균 단계는 도트화에서 3~4ms로 여유, 문제는 글리프 합성 단계. 4-10은 정확성 우선, 4-11에서 도트화와 같은 방식(워밍업 100회 후 300프레임, 중앙값/p95)으로 처음 측정.
9. **검증 방법(4-11)**: ① 결정적 단위 테스트(`FakeGlyphSet`, 밝기 0/128/255 칸 손계산, 독립 레퍼런스도 같은 가짜 글리프 사용) ② 통합(실제 글꼴 경로)에서 속성 검사 — 각 칸 패턴이 문자 세트 글리프 중 하나와 정확히 일치(부분 칸은 잘린 마스크), 칸 밝기와 선택 글리프 잉크 밀도의 단조성, 이진 마스크라면 흰색·검정 두 색뿐 ③ 육안: 사진 형태 합성 그림·패턴 창 저장 이미지, Consolas/Courier New/Monospaced 각각 ④ 음성 대조 4종 이상(매핑 방향 뒤집기, 다른 문자 세트 주입 등) ⑤ 회귀: 효과 1~8 기존 56건 통합 불변 ⑥ 동적: 무작위 전환에 9 포함, 글리프 캐시 생성 비용이 전환 시 지연으로 나타나지 않는지.

## code-writer용 요약 (4-10)
도트화 코드는 이번에 수정하지 않음(정리는 5단계). 글리프 소스 인터페이스 주입, 사전 렌더링 마스크를 정수 연산으로 `int[]`에 합성, 잉크 밀도 자동 정렬과 경계·동점 규칙 문서화, 이진 임계화와 부분 칸 규칙 테스트, effect 패키지 허용·금지 import 규칙 명시, 레지스트리 9번 등록과 `EffectRegistryTest` 번호 기대 갱신, 칸 평균 계산은 별도 메서드로 분리하되 기존 효과는 리팩터링하지 않음, 성능 측정은 4-11.

## ROADMAP 갱신 제안
4′ 행에 도트화 완료 표기. 5단계에 "DataBufferInt 직접 접근 공통화(Identity → Mosaic → Grayscale)"와 "블록 평균 로직 중복 정리" 추가. 6단계 옵션 후보에 디더링, 격자 색·굵기 옵션, ASCII 감마/정규화 추가.
