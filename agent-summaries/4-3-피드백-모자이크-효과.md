## 판정: 4단계 완료 (낮음/정보 항목만 이월)
- 소스 확인: 격자 원점 (0,0), 부분 블록은 실제 픽셀 수로 나눔, 반올림 `(sum+count/2)/count`, 채널 합 long, 입력 `getRGB` 복사로 불변, w==0/h==0은 빈 이미지, blockSize<2 예외. captureOnce는 워커에서 `effect.apply` 후 완성 이미지만 invokeLater로 EDT에 전달, 예외는 `catch (RuntimeException)`으로 잡아 로그 후 스케줄 유지. 요약과 일치.

## 5단계 진입 시 주의점
- **주기**: 현재 `scheduleWithFixedDelay`(처리 후 33ms 대기). 계측 전에는 바꾸지 않음. `scheduleAtFixedRate`는 주기가 일정하나 처리가 길면 작업이 밀려 몰아서 실행되고 CPU가 올라감. 목표 20~30fps는 현재 방식으로도 안일 가능성이 큼 → 실측 후 부족할 때만 조정.
- **이동 직후 한 프레임 지연**: 대응 후보 (1) `componentMoved` 시 즉시 한 번 캡처 트리거 (2) 프레임에 grab 당시 rect를 붙여 현재 rect와 다르면 버림(깜빡임 대신 약간의 정지). 측정해서 선택. 워커가 읽는 captureRect 필드 가시성도 점검.
- **DPI**: 이 PC는 100%뿐. `-Dsun.java2d.uiScale=1.25` 같은 JVM 옵션은 Java2D 스케일만 흉내 내며 `Robot.createScreenCapture`·`getLocationOnScreen`의 실제 DPI 동작(가상화 vs 물리 좌표, DPI awareness)은 시스템 DPI가 다를 때만 정확 → 시뮬레이션 PASS를 'DPI 검증 완료'로 쓰지 않음. 좌표 변환을 순수 함수(논리 ↔ 물리)로 분리해 125%·150% 단위 테스트, JVM 옵션은 보조. 문서에 '코드 리뷰 + 단위 테스트 + 시뮬레이션, 실기 미검증' 명시, 가능하면 사용자가 125%/150% PC에서 1회 확인. Windows 배율을 임시로 바꾸는 것은 사용자 환경 변경이므로 동의 없이 하지 않음.
- **다중 모니터**: 이 PC에서 검증 불가 → `GraphicsEnvironment` 의존을 인터페이스 뒤로 분리해 가짜 모니터 배치(음수 좌표 포함) 단위 테스트 + 코드 리뷰, '실기 미검증' 명시. 사용자가 다중 모니터를 쓸 때만 사용자 확인 요청, 아니면 7단계에서 한계로 문서화. 모니터 경계에 걸친 창에서 Robot이 가상 데스크톱을 한 번에 캡처하는지 코드 리뷰 항목.
- **제외 실패 경고**: 훅에서 실패 시 사용자에게 알리고(메뉴 칸/제목줄 문구 또는 다이얼로그) 로그. 가짜 `DisplayAffinity`가 false를 반환하는 단위 테스트로 충분.
- **장시간 메모리**: 작은 `-Xmx`(예: 128m) + `-Xlog:gc`, 주기적 `jcmd <pid> GC.heap_info`/`GC.class_histogram`, GC 후에도 힙이 우상향하면 누수. Robot으로 이동/리사이즈를 반복시키며 가동. 매 프레임 7MB 할당의 GC 부하·일시정지도 같은 로그로 확인, 재사용 최적화 전후 비교. 검증 단계에 10~15분 확인, 수 시간은 7단계 또는 사용자 환경 가동.
